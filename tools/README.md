# tools

This repository has no build step — publishing is a push — with two exceptions:
the generated index files of a published folder, and the derived `stencils/v5/`
folder (below). The folder the current apps read, and the one edited, is
**`stencils/v6/`** (below); `v5` and older are frozen.

## Before every push

```sh
node tools/check-templates.js                                    # the stencil check over stencils/v6
node tools/generate-stencil-index.js --check --published stencils/v6
node tools/build-v5.js --check                                   # v5 is still v4's derivation
node tools/check-self-contained.js
node --test tools/*.test.js                                      # the tools' own tests
```

Each exits non-zero on a failure. `git diff --stat` against the last push must
show nothing under `stencils/v2*`, `v3`, `v4` or `v5`.

```sh
node tools/generate-stencil-index.js --published stencils/v6          # rewrite stencils/v6/_index.json and _text_syntax.json
node tools/generate-stencil-index.js --check --published stencils/v6  # fail if they are out of date
```

`--published <dir>` names the folder to index; `--out` defaults to the same
folder. **Always pass `--published stencils/v6`** (the folder being edited):
the default, `stencils/v4`, is left over from when v4 was the edited folder,
and v4 is frozen now, so rewriting its index would change a folder installed
apps download. The index files of every frozen folder (`v2.2.x`, `v3`, `v4`,
`v5`) are never regenerated.

| File | What it is |
|---|---|
| `<folder>/_index.json` (today `stencils/v6`) | One row per library placement — `id`, `name`, `category`, `group`, `library`, `library_name` (the library's display name), `file`, `source`, `default_size`, `generated`, `interpret_text`, `has_params`, `text_slots`, `has_title`, and, only when set, `keywords`, `container: true`, `ports` and `connect`. `default_size` is the placement's params, else the template's params, else the template's `default`, else its `libraryview`. `has_title` is true when the template has a title: the first `texts` entry whose `external` is one of the strings `"bottom"`, `"top"`, `"left"`, `"right"`. A title is not counted in `text_slots`. The backend holds it in memory and every stencil search filters it. |
| `<folder>/_text_syntax.json` | For each template whose generator parses its own text: the separator, the markers, an authored one-line note and a worked example. |
| `tools/text-syntax-notes.json` | **Hand-authored input.** One short line per interpreting template. |
| `tools/stencil-keywords.json` | **Hand-authored input.** Search keywords per library and per template id, and the `containers` (libraries and ids) marked `container: true`. The generator validates it and fails, naming the problem, if its shape is wrong or an id or library it names is not in the catalogue. |

Regenerate in the same commit that changes a stencil. Files beginning with `_`
are outputs and are never themselves indexed; no app requests them.

## The cloud-provider files are generated — do not hand-edit them

The 28 `aws_*.json` files (813 shapes) and the Azure/GCP provider files are
generated by `svg2lekh`. Azure has one library per each of its 29 vendor folders
plus `azure.groups`; GCP has `gcp.groups`, `gcp.core_products` and
`gcp.product_categories`. Regenerate them with

```sh
make -C svg2lekh lekhboard      # writes aws_*.json, azure_*.json and gcp_*.json
```

(`LEKHBOARD_V4=<dir>` overrides the destination), then rerun the index generator
in the same commit. Its default destination is `stencils/v4`, which is frozen:
point `LEKHBOARD_V4` at the folder being edited (`stencils/v6`). For an explicitly authorized provider refresh, remove only
the 36 listed legacy Azure/GCP service files with
`LEKHBOARD_V4_REFRESH=1 make -C svg2lekh lekhboard-clean-retired`; the normal
target refuses to copy while those stale paths remain. Do not run that cleanup
after a v4-consuming app ships. A hand edit to generated
output is lost at the next regeneration. Of the sixty-one unrelated files,
thirty-five remain byte-identical to their v3 namesakes; the other twenty-six —
`networks.json`, the ten `office_*.json`, `citrix.json` and the fourteen
`cisco_*.json` — carry titles (below). The six `mscae_*.json` files retain their
paths, IDs and shape data; their library names/category metadata differ from v3,
and they carry titles too. v3 itself remains unchanged, including its 21 old AWS
`aws_*.json` files.

## Hand-authored titles

Unlike the generated provider files, the titles in `networks.json`, `mscae_*.json`,
`office_*.json` and `citrix.json` are hand-maintained data. Each template there has
one `texts` entry, `{"text": <name>, "external": "bottom"}`, with no `location`, and
`"libraryview": {"text": "\n"}`: the picker swaps a non-empty `libraryview.text` into
text slot 0 while it draws the thumbnail, which keeps the title from being drawn
under the icon next to the panel's own label. The title text is the template's name,
unbroken up to three words, two lines of two for four words, and otherwise a line
break after every third word. The `cisco_*.json` templates carry an **empty** bottom
title, appended after any text slots they already had, so a placed Cisco shape can be
given one without changing its slot indices. Server Rack (`rack_*.json`) carries no
titles: a mounted unit's title would sit over the unit below it.

## Two things worth knowing before changing this

**The catalogue has two sources.** `stencils/v4/` is 128 library files: the 28
generated AWS libraries, 61 unrelated libraries retained from v3 (26 of them now
titled), six retained MSCAE libraries relabelled and titled, 30 generated Azure libraries and
three generated GCP libraries; together with the 13 core library files the index
covers 141 files, 5,872 placements and 5,797 distinct ids. The core set adds 27
ids `stencils/v4` does not carry at all, and they are three whole categories —
**Basic**, **Container** and **Arrow**. `avabodh.basic.rectangle` and
`avabodh.container.slv` are core-only, so an index built from the published
folder alone leaves an agent unable to place a plain box or a swimlane. Where an
id is in both sources the published definition wins.

**The generator reads nothing outside this repository.** Its two non-published
inputs are committed here, in `tools/core-stencils/`:

| Folder | What it is |
|---|---|
| `tools/core-stencils/core/` | The core stencil set: 16 JSON files, 13 carrying a `library` array (`connection_arrows.json`, `templates.json` and `libnames.json` are not catalogues). |
| `tools/core-stencils/lua/wireframe_src/` | The 34 wireframe Lua generator sources, scanned for their `split()` flags to derive `_text_syntax.json`'s separators and markers. |

Both were copied byte for byte from the C++ core repository (`lekhcore` `b8d8edc`,
`stencils/core/` and `stencils/lua/wireframe_src/`), which is being retired; from
then on these copies are the source. The C++ apps and the TS apps embed their own
copies of the core set, so a change here does not reach an app by itself.
`--core <dir>` (and `--lua <dir>`, default `<core>/../lua`) point the generator
at another copy, for tests; the generator **fails**, naming the path, if the core
set, one of `basic.json`/`container.json`/`arrow.json`, or a Lua source is
missing, and it fails rather than write a catalogue without the core-only shapes.
`node tools/check-self-contained.js` fails if any tool names a sibling
repository's path.

**A note is not optional.** The separator and the markers are derived from the
flags the Lua script passes to the host's `split()` — the only syntax the C++
`lua_split` actually honours — and the example is the template's own
`generator.text`. Neither can see the syntax that lives in the script body: the
menu's `---` separator row, the tree's icon names, the datagrid's column spec. So
the generator **fails** when a template has `interprettext: true` and no entry in
`tools/text-syntax-notes.json`.

## `stencils/v5` — the folder the TypeScript apps read

`stencils/v5/` is **derived**, never edited: it is `v4` with every Lua generator
replaced by the JS text of the lekhjs module that serves its template id (Work
01M4X7TCHFB862XGT68GPY071C, spec 04 §8). The TS apps (lekhjs `StencilSource`)
and, after the MCP switch, the backend read it; the C++ apps keep reading
`v2.2.x`, `v3` and `v4`, which therefore stay **frozen** with their Lua
`scriptfile`s.

```sh
node tools/build-v5.js            # rewrite stencils/v5 from stencils/v4
node tools/build-v5.js --check    # fail if stencils/v5 is not a fresh derivation of v4
```

Defaults: `--from stencils/v4 --to stencils/v5 --scripts
../lekhjs/src/generators/scripts.generated.json` (the canonical JS texts lekhjs
commits; lekhboard depends on nothing else from lekhjs).

- Every `v4` file is copied **byte for byte**, except a file holding a Lua
  generator (`scriptfile`, or a non-JS `script`) — today only `wireframe.json`.
  There only the `generator` objects are rewritten, in place in the text:
  `script` becomes `/*lekh-js:1:<key>*/…`, `scriptfile` and `type` go, and
  `text`, `interprettext` and `embedrefs` are kept (in that order, after
  `script`). The tool re-parses its output and refuses to write it unless it is
  exactly the converted document.
- The module key comes from the **template id**, through the frozen
  `tools/wireframe-lua-sources.json` (id → Lua source; key
  `wireframe/<source without .lua>`). A Lua generator under an id that is not
  there, or a key with no canonical text, **fails** the build.
- `_index.json` and `_text_syntax.json` are regenerated with
  `generate-stencil-index.js --published stencils/v5` and must equal `v4`'s byte
  for byte, else the build fails. Since a v5 template has no `scriptfile`, the
  index generator finds its Lua source (for the derived text syntax) through the
  same `wireframe-lua-sources.json`.

`v4` and `v5` are **frozen** now (Work 01M4X17CA0RM6T0ZMK4J9VBA1X): neither is
edited and `build-v5.js` is never rerun to write. Installed apps download both,
and a changed file would reach them with no app release. `build-v5.js --check`
stays in the pre-push list only to prove that `v5` is still exactly its
derivation of `v4`. A stencil change goes into `v6` (below).

## `stencils/v6` — the folder that is edited (Work 01M4X17CA0RM6T0ZMK4J9VBA1X)

An existing `stencils/vN` folder is **never edited**: installed apps download
from it, and a changed file reaches them with no app release. So a published
change goes into a new folder:

1. `stencils/v6/` was made as a byte copy of `v5` (`cp -a stencils/v5
   stencils/v6`), committed on its own.
2. Then `v6` was edited directly: a closed `bound` on
   `avabodh.flowchart.multiple_documents`, `avabodh.flowchart.collate`,
   `avabodh.misc.node`, `avabodh.misc.package` and `avabodh.misc.component`, so
   a connector end lands on the whole outline (each `bound` uses only `data`
   points the template's `draw` paths already use).
3. Its index files are regenerated in the same commit:
   `node tools/generate-stencil-index.js --published stencils/v6`. A row carries
   `ports` and `connect` when its template sets them (copied as written).

The apps read `v6` once lekhjs `STENCIL_LIB_VERSION` is `'v6'`. `v6` is edited
directly — no tool derives it, and `build-v5.js` does not touch it — until it
is released. **The next published change after that makes `v7` the same way**:
copy `v6` to `v7` in one commit, edit `v7`, regenerate `v7`'s index, and move
`STENCIL_LIB_VERSION` (and every consumer of the folder name) to `v7`.

### `check-templates.js` — the stencil check

```sh
node tools/check-templates.js [dir…]    # default: stencils/v6
```

Checks every template of every library file in each folder (the `_*.json`
outputs are skipped) and exits 1 with one line per failure — file, template id,
code. The codes: `port_without_id`, `port_duplicate_id`,
`port_index_out_of_range`, `port_dir_unknown`, `connect_value_unknown`,
`connect_ports_without_ports`, and `boundary_not_closed` (the template sets
`primitive_for_intersection`, has no `bound`, and its first draw path is not
closed; a template the engine never connects to — an open polygon, an open path
template or a Bézier curve with no `connect` and no port, or `connect: "none"` —
is exempt). The engine keeps the same rules in its own module; this is
lekhboard's copy, and both suites share the fixtures in
`tools/fixtures/check-templates/` by content. Its tests:
`node --test tools/*.test.js` (Node 22 and later take test globs, not a bare
folder).
